# Known issues

_Last updated: 2026-07-28. Reviewers: TBD._

All Module 4 verification scripts and the GST/pricing pure unit tests pass at 100% as of this writing — see `08-verification.md` for current per-script counts and the full-regression baseline. The issues below are the record of what was actually found broken (and, in each case, fixed) during Module 4's development, plus a record of spec-level issues found while writing verify scripts and while implementing Tasks 4.6/4.7, kept for the same reason Modules 2/3's own `known-issues.md` files keep theirs: so nobody re-discovers the same rake.

## Fixed in Task 4.7

Task 4.7 shipped the first real client reference PDFs this module has ever had (`fixtures/reference-pdfs/PTT-150.pdf`, `PTT-151.pdf`, `PTT-152.pdf`) and used them as the visual acceptance gate (Rule 13), not just the automated `verify-pdf.sh` checks. Comparing the actual rendered output against them surfaced several real gaps beyond the task's own literal instructions (Rule 9: fix in the same commit; Rule 10: the PDFs win over spec prose):

- **Proforma split.** `invoice-performance.hbs` (v1.0.0) was split into `invoice-proforma-local.hbs` and `invoice-proforma-outstation.hbs` (v1.1.0 only — v1.0.0 is untouched and still resolves for any invoice whose `pdf_template_version` is still `v1.0.0`, per ADR-015). `invoice_type` stays `PERFORMANCE` in the DB enum; "Proforma" is a template/label choice, not a renamed value.
- **Extra-KM/Extra-Hrs breakdown was previously combined, not shown.** PTT-150 (and the task's own Part B column list, which happens to match PTT-152 exactly) both show a `Extra KM | Rate/KM | Extra KM Amount | Extra Hrs | Rate/Hr | Extra Hrs Amount` breakdown that `invoice_lines.extras_amount_paise` doesn't store — it only stores the combined sum. The split IS derivable without any schema change: `trip_sheets.snap_base_km` / `snap_base_hours` / `snap_extra_km_rate_paise` / `snap_extra_hr_rate_paise` (Task 3.x snapshot columns) already hold everything needed (`extra_km = total_km - snap_base_km`, etc.) — `invoiceLine.repository.js#listByInvoiceForPdf`'s join was widened to pull them in. This is a read/rendering-layer enrichment only; no migration, no change to how GST or any total is actually computed.
- **Per-line Toll/Parking (LOCAL) and Toll Charges + Total Cost (OUTSTATION) columns were missing.** Same resolution as above — `trip_sheets.toll_paise`/`parking_paise` are real, already-stored per-trip columns, joined in the same widened query, not fabricated.
- **`invoice-outstation-tax.hbs` (v1.1.0) column set corrected to match PTT-151 exactly**: dropped `Trip Sheet No.` and the generic `Extra Charges` column, reordered `Vehicle Type` before `Vehicle Number`, added `Toll Charges`/`Total Cost`. See "PTT-151 drops trip-sheet traceability" below — this was followed literally per Rule 10 even though it trades away an audit-trail column LOCAL invoices keep.
- **B2C GSTIN/State hiding** (`shared/bill-to.hbs`) already existed as of v1.0.0 (`{{#if customer.gstin}}`) — Task 4.7 only added the explanatory comment and confirmed all four invoice templates (2 tax + 2 proforma) and `credit-note.hbs` share the one partial.
- **`Place of Supply` leaked onto the Proforma header despite never being passed to it.** Handlebars partials inherit the *entire* parent render context, not just explicitly-passed hash arguments — `invoice-proforma-{local,outstation}.hbs` never pass `placeOfSupplyStateName` to `shared/header.hbs`, but the field is still a top-level key on the render context (needed by the TAX templates), so it rendered anyway. Fixed by gating the Place-of-Supply block on the same `hideTenantTaxInfo` flag already used to hide the tenant's own GSTIN/PAN/State on Proforma docs. Caught only by rendering a sample PDF and reading it — every automated check passed regardless, same class of gap ADR-015 already generalizes.
- **`Booked By` (Service Details block) was never rendered**, despite `trip_sheets.booked_by` being a real, already-user-settable field (Task 3.x) and every one of PTT-150/151/152 showing it. Added using the first line's trip, same "first line is authoritative" reasoning `pickInvoiceTemplateName` already uses for `service_type`.

## Discovered while building Task 4.6: quick-create's B2B GSTIN requirement can't actually be waived

**Symptom (would have been):** the Task 4.6 spec asked for `gstin` to be optional even for a B2B quick-create ("some B2B clients don't have GSTIN registration"), with the new endpoint skipping `createCustomer`'s own application-layer `B2B_REQUIRED_FIELDS` check to allow it.

**Root cause:** `customers_b2b_required_fields` (Task 2.3) is a DATABASE CHECK constraint — `customer_type <> 'B2B' OR (company_name IS NOT NULL AND gstin IS NOT NULL AND state_code IS NOT NULL)` — completely independent of any application-layer check. Skipping the JS-level check doesn't change the outcome at all: the INSERT still fails at the database, just one layer lower. Task 4.6's own constraints explicitly rule out schema changes, so relaxing or dropping this CHECK to actually honor the spec's literal request was not an available option.

**Status:** RESOLVED — as designed, not as originally specified. A B2B quick-create without a `gstin` is rejected with a clean `400 B2B_REQUIRED_FIELDS` (the existing `customer.repository.js#mapConstraintError` translation, not a raw constraint-violation leak) — the same outcome as the full `POST /customers` endpoint would give. What quick-create actually simplifies for a B2B customer is the field list and the `company_name`-defaults-to-`name` convenience, not the GSTIN requirement itself, which remains a real, unbypassable invariant of this schema. See ADR-014, `customer.service.js#quickCreateCustomer`'s own top comment, and `scripts/verify-customer-quick-create.sh`'s Step 2 (which asserts the correct, actual behavior rather than the originally-specified one).

## Task spec issues (documentation-only — no code changes beyond what's already recorded above; kept so the same example data or assumption doesn't get reused uncritically)

- **Task 4.1's spec instructed copying `trip.extras_amount_paise` onto every invoice line unconditionally**, which would tax an OUTSTATION trip's pure-agent reimbursements (parking/permit/fasttag) as service revenue — a real GST compliance defect, not a cosmetic one. The same spec's own worked example (a Cauvery-reference trip) contradicted this instruction once checked: it asserted a line subtotal excluding the reimbursement entirely, then added the exact reimbursement figure back in as a separate invoice-level field. See ADR-010 for the full resolution.
- **Task 4.3's `buildTenantSnapshot`/`buildCustomerSnapshot` spec assumed flat address/phone/email/website columns on `tenants` and `customers`** that don't exist in this schema (`tenants` has none of those at all; `customers`' address is one nested JSONB blob). Resolved by reading the actual schema and building the snapshot from what's really there — see ADR-014 and `src/utils/invoiceSnapshot.js`'s own top comment.
- **Task 4.5's PDF-template spec assumed `tenants.tagline`/`phone2`, an invoice-level `reverse_charge` column, and a per-line KM/hour rate breakdown on `invoice_lines`** — none of which exist. Resolved by rendering only real fields; "Place of Supply" is derived from the customer's own `state_code` (the standard GST convention: the recipient's state) rather than a fabricated invoice column. See ADR-014 and `src/services/pdf.service.js`'s own top comment (five separate instances of this same class of gap, documented in full there).
- **Task 4.5's state-code lookup was initially keyed by the official numeric CBIC GST code** (`"29"` → Karnataka), but this application's own `state_code` columns are 2-letter abbreviations (`"KA"`), derived from a GSTIN's leading digits (`src/utils/gstin.js#GST_STATE_MAP`). Every lookup silently missed, and "Place of Supply" never rendered on any PDF — caught only by rendering a sample PDF and reading it, since every automated `verify-pdf.sh` check passed regardless (none of them inspect which fields actually appear on the rendered page). See ADR-015, which generalizes this into a standing requirement that document-rendering tasks include a visual-review step.
- **Recurring across Tasks 4.1-4.5, inherited from the same convention Module 3 established: task specs' hardcoded example dates drift into the future relative to whenever a verify script actually runs.** Every verify script in this module computes its trip/invoice/payment dates as offsets *before* today (`date -v-Nd`) rather than hardcoding a calendar date (Rule 8).

## Deferred

- **Schema enrichment for tenant business info shown on PDFs — correction: the client's real reference PDFs DO need this, unlike what Task 4.6 assumed.** Task 4.6's known-issues entry (before this module had ever seen a real client reference PDF) claimed "the client's actual reference PDFs render correctly without these as separate columns." Task 4.7 obtained the first real reference PDFs (`fixtures/reference-pdfs/PTT-150/151/152.pdf`) and that claim does not hold: PTT-150/151 both show a tagline ("Car Rental & Outstation Cab Services"), a full postal address, and a phone/email line in the sender header, none of which any `tenants` column currently stores (only `name`/`gstin`/`pan`/`state_code`/`logo_url`/`bank_details`/`gst_rate`/the numbering prefixes exist). They also show a jurisdiction sentence ("Subject to Bangalore jurisdiction") in the footer, which would need a tenant `city` (or free-text jurisdiction) field this schema doesn't have either. None of this was added in Task 4.7 — it's a schema change (new `tenants` columns + a `settings.validator.js` update + a UI to capture them), and Task 4.7's own constraints rule that out ("zero schema migrations"). Still deferred, but now correctly described as a real, confirmed gap rather than a non-issue.
- **Bank-details PAN.** PTT-150/151/152's Bank Details block shows a PAN line (`PAN: BQSPR7829H`) distinct from the tenant's own PAN already shown in the header — almost certainly the bank-account holder's PAN, not the business PAN. `tenants.bank_details` (JSONB) has no `pan` key today (`settings.validator.js#bankDetailsSchema` is an `.unknown(false)` allowlist of `account_name`/`account_number`/`ifsc`/`bank_name`/`branch`/`upi_id`). Not added in Task 4.7 — there's no existing data to source it from (unlike the extra-KM/toll fixes, which reused already-captured trip data), so rendering it would mean inventing a value, which Task 4.7's own instructions explicitly rule out ("mark TODO if unverifiable" rather than guess).
- **Reverse Charge.** PTT-150/151 both show a `Reverse Charge: No` line in the header; `invoices` has no `reverse_charge` column, and under GST law renting a motor vehicle to a body corporate CAN be subject to the reverse-charge mechanism under specific conditions (recipient is a body corporate, supplier hasn't opted to pay under forward charge) — this isn't safely always "No" and isn't derivable from anything currently on the `invoices`/`customers` schema. Deliberately left unrendered rather than hardcoded, since a wrong reverse-charge declaration on a real tax document is a compliance risk, not a cosmetic gap.
- **PTT-151 (OUTSTATION tax) drops the `Trip Sheet No.` column that PTT-150 (LOCAL tax) keeps.** Followed literally per Rule 10 (the reference PDF wins over uniform column parity across service types), but this trades away the one column that lets someone trace an invoice line back to its source trip sheet without opening the invoice in the app. Worth confirming with the client whether this is intentional or an oversight in their reference document before the OUTSTATION layout is treated as final.
- **A Proforma invoice built from a genuinely flat-rate `billing_mode='PERFORMANCE'` trip renders blank Extra KM/Extra Hrs/Rate columns.** The invoiceable-trips picker (`tripSheet.repository.js#findInvoiceableForCustomer`, Task 4.1) does not filter by `billing_mode` at all — any FINALIZED, unheld trip, regardless of how it was priced, can be placed on either a TAX or a PERFORMANCE/Proforma invoice. PTT-152's layout (package + extra-KM/Hrs breakdown) assumes the underlying trip was priced with a `LOCAL_PACKAGE` or `OUTSTATION_SLAB` rule, which is what a real "preview of a future tax invoice" Proforma actually is in this business. A trip priced with the flat-rate `PERFORMANCE` rule (`total_km × per_km_rate + flat batta`, no package, no extra-KM concept) has no `snap_base_km`/`snap_extra_km_rate_paise` to derive from, so those columns render as blank/zero rather than a fabricated number — a graceful degradation, not a crash, but worth knowing about if a real Proforma ever looks sparser than expected. Not fixed in Task 4.7 (would mean changing the picker's filtering, a domain-layer change out of scope).
- **GSTR-1 file export.** No file in a government e-filing format is produced anywhere in this module. Real implementation is post-launch, pending confirmation of the exact format required.
- **Email delivery.** Deferred entirely — nothing in this module sends a generated PDF or a notification anywhere.
- **Cloud PDF storage.** PDFs live on the local filesystem (`PDF_STORAGE_ROOT`) for now — see `05-design-decisions.md` for the reasoning and what a move to object storage would require.
- **Payment receipt PDFs.** Only invoice and credit-note documents are rendered; a document confirming a payment was received is not built.
- **Invoice listing/search (`GET /invoices`).** There is no list endpoint for invoices anywhere in this module — only `GET /invoices/:id` (single-invoice fetch). A frontend needing to browse/search invoices has nothing to call yet; this is a gap for a future task, not a deliberate design decision documented anywhere else in this folder.
