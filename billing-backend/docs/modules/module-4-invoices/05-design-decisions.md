# Design decisions

_Last updated: 2026-07-23. Reviewers: TBD._

This document explains the *why* behind choices that aren't self-evident from reading the code. Several of these have a standalone ADR (`docs/adr/`); where that's the case, this section is the short version and the ADR is the long version with alternatives spelled out.

## Why snapshot at issue, not at draft

`tenant_snapshot`/`customer_snapshot` are `NULL` for the entire time an invoice is a DRAFT and are populated exactly once, at the moment `POST /invoices/:id/issue` succeeds. Snapshotting at draft-creation time instead would freeze state a user might still be actively editing the trip set or charges against — a legal, unchanging record only needs to exist once the document itself becomes legally final, and that moment is issue, not draft creation. Freezing earlier would also mean re-editing a draft (changing the trip set, adjusting a discount) could never legitimately need "fresher" tenant/customer data, since it was already locked in — exactly backwards from what a DRAFT is for. See `02-architecture.md` and ADR-014 for the related gap found in the snapshot builders' own field list versus the actual schema.

## Why gap-free numbering per FY, per invoice type, per tenant

Indian GST law requires tax invoice numbering to have no gaps within a fiscal year for a given series. A `DRAFT` invoice therefore carries `invoice_number = NULL` and never touches the numbering sequence at all — only `POST .../issue` allocates a number, and it does so atomically, inside the same transaction as every other consequence of issuing (snapshot freeze, trip transitions), so a failure partway through never leaves a burned number with no corresponding issued invoice. `TAX` and `PERFORMANCE` invoices draw from independent sequences (`invoice_number_sequences`' composite key includes `invoice_type`) since they use different prefixes and, strictly, only `TAX` invoices are subject to the legal gap-free requirement — `PERFORMANCE` numbering follows the same discipline anyway, for consistency rather than legal necessity.

## Why credit notes instead of invoice deletion

An issued tax invoice is a legal document under Indian GST; deleting one as though it never existed is not how a legitimate reversal works, and would leave no audit trail of what was billed and why it was undone. Cancelling an `ISSUED`/`PAID` invoice instead creates a `credit_notes` row — its own gap-free numbering, its own snapshot of tenant/customer state as of the cancellation moment, and financial figures mirroring the original invoice's frozen totals as the reversal amount — while the original invoice itself is marked `CANCELLED`, not removed. A `DRAFT` invoice, by contrast, was never legally issued in the first place, so cancelling one is a plain status flip with no credit note at all; there is nothing to reverse for GST purposes.

## Why one invoice_type_enum with TAX and PERFORMANCE (not three, including a PROFORMA the client also uses internally)

The client's own reference documents include a third format, Proforma (`PTT/2026-27/152`), explicitly named out of scope for this module. `invoice_type_enum` only has two values — `TAX` and `PERFORMANCE` — because those are the two document types this module actually implements end to end (numbering, GST rules, PDF templates); adding a third enum value with no corresponding behavior anywhere would be dead schema, not a real option. If Proforma support is added later, it would need its own numbering sequence, its own GST treatment decision, and its own PDF template — a real addition, not a one-line enum extension.

## Why single service_type per invoice (all LOCAL or all OUTSTATION)

Task 4.3 enforces that every trip added to one `TAX` invoice shares the same `service_type`. The Yellow (Local) and Blue (Outstation) reference documents are structurally different layouts — different columns, different per-line arithmetic (package-plus-extras versus running-km-plus-batta) — not the same table with a cosmetic toggle. Mixing `LOCAL` and `OUTSTATION` trips on one invoice would leave no single coherent table layout to render, and `pdf.service.js#pickInvoiceTemplateName` relies on this invariant directly: it looks at only the *first* line's `service_type` to decide Yellow versus Blue, trusting that every other line agrees.

## Why manual_override flags on the four reimbursement columns

`toll_manual_override`/`parking_manual_override`/`permit_manual_override`/`fasttag_manual_override` (Task 4.2) exist because auto-summing these four columns from the selected trips is the common case, but a user's explicit correction to one of them needs to survive a later trip-set change without being silently recomputed away. `computeEffectiveReimbursements`'s precedence is: an explicit value in THIS request always wins and sets the flag; otherwise, if the flag is already `true` from an earlier request, the existing value carries over unchanged; otherwise, fall back to a fresh auto-sum. An explicit `0` counts as an override too — checked via `!= null`, not truthiness — since "no fasttag on this invoice" is a real, intentional answer a user gave, not silence to be overwritten on the next edit.

## Why PAID is a derived transition, never set directly

Nothing in this codebase ever sets `invoices.status = 'PAID'` as a direct write from a caller-supplied value. `payment.service.js#maybeTransitionToPaid` re-queries the actual sum of `RECORDED` payments against the invoice every time a payment-affecting action happens (recording a payment, applying an advance, cancelling a payment) and transitions the invoice based on that fresh number, in both directions — `ISSUED → PAID` when the sum reaches `net_payable_paise`, and the mirror-image `PAID → ISSUED` when cancelling a payment drops the sum back below it. Trusting a client-supplied "mark as paid" flag instead would let the invoice's own status drift out of sync with what was actually, verifiably paid — the whole point of deriving it is that the two can never disagree. This is the same "the state machine encodes every legal transition, including derived ones, not just user-initiated ones" principle (Rule 12) that led to `PAID → ISSUED` being added as a first-class entry in `invoiceLifecycle`'s own `TRANSITIONS` map rather than a special case bolted onto the payment service.

## Why over-payment auto-splits into an advance

Recording a payment larger than an invoice's outstanding balance has exactly two coherent options: reject it outright, or accept it and do something sensible with the excess. This codebase accepts it and splits: the outstanding amount applies to the invoice (bringing it to fully paid), and the excess becomes a new, separate unallocated advance on the same customer, linked back to the applied portion via `parent_payment_id` for audit. Rejecting the payment outright would be a worse experience for a genuinely common real-world case — a customer rounds up or pays a lump sum covering more than one thing — and manually creating a separate advance entry after the fact is exactly the bookkeeping step this split automates. See ADR-013 for the synthetic-reference-uniqueness problem the split introduced and how it was resolved.

## Why payments cancel, not delete

There is no `DELETE` route or repository function for a `payments` row anywhere in this module. `POST /payments/:id/cancel` is the only reversal path, flipping `status` to `CANCELLED` and requiring a reason — the same "cancellation is an audited event, not an erasure" principle Module 3 already applies to trips and this module applies to invoices via credit notes. A cancelled payment still exists in the table, contributing nothing to `sumRecordedForInvoice`'s total, but visible in `GET /payments`/the customer ledger for audit; a deleted row would leave no trace that money was ever recorded and then reversed.

## Why invoice lines carry only taxable service revenue (ADR-010)

See ADR-010 for the full record. In short: `trip_sheets.extras_amount_paise` means "extra-km/extra-hour service revenue" for a `LOCAL` trip but "parking + permit + fasttag reimbursements" for an `OUTSTATION` trip — two different tax categories under the same column name. Copying it onto an invoice line unconditionally, as an early draft of the Task 4.1 spec suggested, would tax a pure-agent reimbursement as though it were revenue. `invoice_lines.extras_amount_paise` is populated from the trip only for `LOCAL` trips; `OUTSTATION` reimbursements are captured as invoice-level aggregate columns instead, added after the GST computation.

## Why Puppeteer + Handlebars for PDFs

Puppeteer (headless Chrome) plus Handlebars templates was chosen over a pure-JS PDF-drawing library (`pdfkit`, `pdf-lib`, and similar) because the client's reference documents are laid out as HTML tables would naturally render — bordered grids, colored header rows, a totals block with clean alignment — and building that same layout with a drawing-primitives API (explicit x/y coordinates for every line and cell) is both slower to build and far more fragile to adjust than editing an HTML/CSS template. The cost is a genuinely heavy runtime dependency (a full browser engine) and the corresponding install/deployment complexity — mitigated in this environment by using `puppeteer-core` against an already-installed system Chrome rather than the full `puppeteer` package's bundled ~300MB download, which stalled indefinitely under this environment's network conditions (see `07-debugging-playbook.md`).

## Why template versioning

Every generated PDF stores the exact template version (`pdf_template_version`) used to produce it, and regenerating an already-issued document's PDF always re-renders with that STORED version, never the current default (`pdfEngine.TEMPLATE_VERSION`). A future layout change (a new template version directory) therefore never silently alters the appearance of a document that was already issued and possibly already sent to a customer — which would be a real problem for a legal tax document whose visual content a business might need to defend as unchanged since the date it was issued.

## Why filesystem PDF storage, for now

Generated PDFs are written to `PDF_STORAGE_ROOT` (a configurable local directory, default `./pdf-storage`, gitignored) rather than an object-storage service (S3-compatible or similar). For a single-server deployment, this is simpler to reason about and requires no additional credentials, network calls, or failure modes beyond the local filesystem already being available — and every current consumer (the `GET .../pdf` download route) reads the file back on the same server that wrote it, so there's no cross-server access problem to solve yet. This is explicitly not the final answer for a multi-instance deployment, where a request served by a different server instance than the one that generated the file would fail to find it; moving to object storage would require replacing `writePdfFile`/`resolveStoredPath` in `pdf.service.js` with equivalent upload/signed-URL logic, but nothing else in the PDF-generation flow (template rendering, snapshot-sourced context, versioning) would need to change.

## Why PDF generation is synchronous, not an async queue

`POST .../pdf` blocks until the PDF is fully rendered and written, then returns its metadata — there is no job queue, polling endpoint, or webhook. Puppeteer rendering for a single-page invoice takes well under a second in practice, which is fast enough for a synchronous HTTP request without a noticeably degraded user experience, and a synchronous flow means the client gets an immediate, unambiguous success/failure result with no separate "check back later" step to build against. If invoices grew to multi-page documents or PDF volume grew high enough that Puppeteer rendering became a request-latency problem, this would be the point to introduce an async queue — nothing about the current design (idempotent regeneration, versioned templates, snapshot-sourced rendering) would need to change to add one later, since the queue would just be a different way of invoking the same `generateInvoicePdf`/`generateCreditNotePdf` functions.

## Why a quick-create customer endpoint

`POST /customers/quick-create` (Task 4.6) exists because the full `POST /customers` endpoint's field list — company name, GSTIN, PAN, state code, address, credit terms — is more than a front-desk operator wants to fill out mid-flow when creating a trip or invoice for a walk-in customer they've never seen before. Quick-create accepts only `customer_type`, `name`, and a few optional fields, reusing the exact same insertion path (`customerRepository.insert`) the full endpoint uses rather than a separate, parallel creation flow. One consequence of this had to be reconciled with reality during Task 4.6: the spec asked for GSTIN to be optional even for a B2B customer here, but `customers_b2b_required_fields` is a hard DATABASE CHECK constraint (Task 2.3, unrelated to this module) requiring a GSTIN for every B2B customer regardless of which application code path creates one — and this task's own scope explicitly excludes schema changes. A B2B quick-create without a GSTIN therefore still fails, exactly as it would through the full endpoint, just via a cleanly-mapped `400 B2B_REQUIRED_FIELDS` rather than either silently succeeding (impossible without a migration) or leaking a raw constraint violation. See ADR-014 and this file's API reference entry for the endpoint.

## Why reports:read now includes viewer

`reports:read` originally excluded both `staff` and `viewer` (Task 4.4), on the reasoning that receivables/aging data is financial reporting, a step up from an operational read like `invoices:read`/`payments:read`. Task 4.6 revisited this specifically for `viewer`: this system's `viewer` role is, by design, the read-only role — every other `:read` permission in the matrix already includes it, and there was no articulated reason the aging report specifically should be the one read-only surface a viewer can't see. `staff` remains excluded; that role is operational (front-desk data entry: creating trips, recording payments), not analytical, and the aging report doesn't serve an operational task the way recording a payment does.
