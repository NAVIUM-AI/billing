# Error code reference

_Last updated: 2026-07-18. Reviewers: TBD._

Every `apiError(...)` call site in the entire codebase, not just Module 2's own files — a request to any Module 2 endpoint can surface a shared/Module-1 code (auth, RBAC, generic validation) as easily as a Module-2-specific one, so this table is deliberately exhaustive across `src/` rather than scoped only to files Module 2 introduced. Verified by walking every `.js` file under `src/` and extracting every `apiError(status, "CODE", ...)` call site programmatically; codes marked **(shared)** originate in Module 1 middleware/services but apply to every request in the system, Module 2 included.

Every error response follows `{ "error": { "code", "message", "details"? } }` (see `src/middleware/errorHandler.js`); the `Fix` column below is what a caller (or the engineer debugging a caller) should actually do.

| Code | HTTP | When it fires | Where (file) | Fix |
| --- | --- | --- | --- | --- |
| `ACCESS_TOKEN_EXPIRED` **(shared)** | 401 | The JWT access token's `exp` has passed | `src/middleware/authenticate.js` | Call `POST /auth/refresh` to get a new access token |
| `ALREADY_SUPERSEDED` | 400 | `POST /pricing/rules/:id/supersede` targets a rule whose `effective_to` is already set to a date at or before the new rule's `effective_from` | `src/repositories/pricingRule.repository.js` | Supersede the currently-open (`effective_to IS NULL`) rule in the chain instead of a closed one |
| `AUTH_INVALID` **(shared)** | 401 | JWT fails signature/shape verification, or (on `GET /auth/me`) the token is valid but the user it points to no longer exists | `src/middleware/authenticate.js`, `src/api/v1/auth.routes.js` | Log in again |
| `AUTH_REQUIRED` **(shared)** | 401 | No `Authorization` header, or a permission/role check ran before `authenticate` populated `req.user` | `src/middleware/authenticate.js`, `src/middleware/requirePermission.js`, `src/middleware/requireRole.js` | Include a valid `Authorization: Bearer <token>` header |
| `B2B_REQUIRED_FIELDS` | 400 | Creating/updating a customer with `customer_type: "B2B"` and missing `company_name`, `gstin`, or `state_code` | `src/services/customer.service.js` (pre-check), `src/repositories/customer.repository.js` (DB CHECK backstop) | Supply all three required B2B fields |
| `B2C_REQUIRED_FIELDS` | 400 | The DB CHECK `customers_b2c_required_fields` fires (a B2C row with no `name`) — reachable only if a request somehow bypasses the Joi-level B2C name requirement | `src/repositories/customer.repository.js` | Supply `name` for a B2C customer |
| `CANNOT_DEACTIVATE_OWNER` | 403 | Attempting to deactivate the tenant's `owner` user via user management | `src/services/user.service.js` | Ownership transfer is a separate, deliberate flow — not applicable to Module 2 directly, listed here because it shares the error taxonomy |
| `CANNOT_DEACTIVATE_SELF` | 403 | A user attempts to deactivate their own account | `src/services/user.service.js` | Have another authorized user perform the deactivation |
| `CANNOT_DEMOTE_SELF` | 403 | The `owner` attempts to change their own role away from `owner` | `src/services/user.service.js` | Ownership transfer is a separate flow |
| `CANNOT_MODIFY_OWNER` | 403 | Anyone other than the owner attempts to change the owner's role | `src/services/user.service.js` | Not supported — ownership transfer is a separate flow |
| `CONTACTS_B2B_ONLY` | 400 | `POST /customers/:id/contacts` targets a customer whose `customer_type` is `B2C` | `src/services/customer.service.js` | Contacts only apply to B2B customers; a B2C customer's own `phone`/`email` is its only contact point |
| `CONTACT_PRIMARY_CONFLICT` | 409 | Two concurrent "add contact with `is_primary: true`" requests race past the pre-check flip and both attempt to insert as primary; the second hits `ux_customer_contacts_one_primary` | `src/repositories/customer.repository.js` | Retry the request |
| `CUSTOMER_ARCHIVED_EXISTS` | 409 | Creating a customer whose `gstin` or `phone` matches an existing, archived (`is_active = false`) customer | `src/services/customer.service.js` | Call `POST /customers/:id/unarchive` on the returned `customerId` instead of creating a new record |
| `CUSTOMER_GSTIN_ALREADY_EXISTS` | 409 | Creating/updating a customer with a `gstin` already used by another *active* customer in the same tenant | `src/repositories/customer.repository.js` | Use the existing customer, or correct the GSTIN |
| `CUSTOMER_NOT_FOUND` | 404 | `customerId` doesn't exist, or belongs to a different tenant (indistinguishable by design — see `07-debugging-playbook.md`) | `src/services/customer.service.js` | Verify the id and that you're authenticated as the owning tenant |
| `CUSTOMER_PHONE_ALREADY_EXISTS` | 409 | Same as `CUSTOMER_GSTIN_ALREADY_EXISTS`, for `phone` | `src/repositories/customer.repository.js` | Use the existing customer, or correct the phone number |
| `DRIVER_ARCHIVED_EXISTS` | 409 | Creating a driver whose `phone` or `license_number` matches an existing, archived driver | `src/services/driver.service.js` | Call `POST /drivers/:id/unarchive` on the returned `driverId` |
| `DRIVER_LICENSE_ALREADY_EXISTS` | 409 | Creating/updating a driver with a `license_number` already used by another *active* driver in the tenant | `src/repositories/driver.repository.js` | Use the existing driver, or correct the license number |
| `DRIVER_NOT_FOUND` | 404 | `driverId` doesn't exist, or belongs to a different tenant | `src/services/driver.service.js` | Verify the id and tenant |
| `DRIVER_PHONE_ALREADY_EXISTS` | 409 | Same as `DRIVER_LICENSE_ALREADY_EXISTS`, for `phone` (normalized comparison, so formatting variants collide correctly) | `src/repositories/driver.repository.js` | Use the existing driver, or correct the phone number |
| `EMAIL_ALREADY_EXISTS` **(shared)** | 409 | Signup with an email that exists under any tenant, or `POST /users` with an email already used within the same tenant | `src/services/auth.service.js`, `src/services/user.service.js` | Use a different email, or log in with the existing account |
| `EMPTY_PATCH` | 400 | A `PATCH` request's body, after the repository's column whitelist is applied, contains zero updatable fields | `src/repositories/vehicle.repository.js`, `driver.repository.js`, `customer.repository.js`, `pricingRule.repository.js` | Include at least one field the endpoint actually allows updating (in practice this is defended against earlier by each validator's own `.min(1)`, so reaching this code from a real request is unlikely — see `07-debugging-playbook.md`) |
| `FORBIDDEN` **(shared)** | 403 | The authenticated user's role isn't listed for the permission key the route requires (`src/config/accessMatrix.js`) | `src/middleware/requirePermission.js`, `src/middleware/requireRole.js` | `error.details.required` names the permission key, `error.details.role` names the caller's role — log in as a user with that permission |
| `GSTIN_STATE_MISMATCH` | 400 | A B2B customer's GSTIN and `state_code` are both provided (or both resolvable after a patch) and the GSTIN's embedded state doesn't match `state_code` | `src/services/customer.service.js` | `error.details.gstin_state` names what the GSTIN encodes; correct either the GSTIN or `state_code` so they agree |
| `INVALID_CALCULATION_INPUT` | 400 | `POST /pricing/preview` called with `usage` that's missing fields the resolved rule's calculator requires, or with invalid values (negative, non-integer) | `src/services/pricingRule.service.js` (`previewCalculation`) | `error.details.field` names the exact input at fault, `error.details.reason` is a stable machine-readable cause (`RULE_FIELD_MISSING`, `USAGE_INVALID`, `RULE_TYPE_UNKNOWN`); send all fields the `rule_type` requires — see the calculator files in `src/domain/pricing/` for each shape's requirements |
| `INVALID_CREDENTIALS` **(shared)** | 401 | Login with a wrong password or an email that doesn't exist — same code for both, deliberately, to avoid leaking which accounts exist | `src/services/auth.service.js` | Check the email and password |
| `INVALID_DATE_RANGE` | 400 | The DB CHECK `pricing_effective_range` fires (`effective_to <= effective_from`) — reachable only if a request bypasses the Joi-level cross-field check | `src/repositories/pricingRule.repository.js` | Ensure `effective_to` is strictly after `effective_from` |
| `INVALID_FORMAT` | 400 | A customer's GSTIN/PAN/state_code fails its DB-level format CHECK — reachable only if a request bypasses the corresponding Joi validation | `src/repositories/customer.repository.js` | `error.message` names the specific constraint that failed (e.g. `customers_gstin_format`) |
| `LOCAL_FIELDS_MISSING` | 400 | Creating/superseding a `LOCAL_PACKAGE` pricing rule without all of `base_hours`, `base_km`, `base_price_paise`, `extra_km_rate_paise`, `extra_hr_rate_paise` | `src/services/pricingRule.service.js` (pre-check), `src/repositories/pricingRule.repository.js` (DB CHECK backstop) | `error.details.missing_fields` lists exactly which ones; supply them (as their `*_rupees`/integer wire equivalents) |
| `NOT_FOUND` **(shared)** | 404 | No route matches the request path at all | `src/app.js` | Check the URL and HTTP method |
| `NO_APPLICABLE_RULE` | 404 | `GET /pricing/rules/applicable` or `POST /pricing/preview` finds no pricing rule covering the given (rule type, vehicle type, date) | `src/services/pricingRule.service.js` | `error.details` names the query that missed; create or supersede a rule effective on that date |
| `OUTSTATION_FIELDS_MISSING` | 400 | Same as `LOCAL_FIELDS_MISSING`, for `OUTSTATION_SLAB` (`slab_rate_paise`, `min_km_per_day`, `driver_batta_per_day_paise`) | `src/services/pricingRule.service.js`, `src/repositories/pricingRule.repository.js` | Supply all three |
| `PERFORMANCE_FIELDS_MISSING` | 400 | Same, for `PERFORMANCE` (`per_km_rate_paise`, `performance_batta_paise`) | `src/services/pricingRule.service.js`, `src/repositories/pricingRule.repository.js` | Supply both |
| `PRICING_RULE_NOT_FOUND` | 404 | `ruleId` doesn't exist, belongs to a different tenant, or (inside `supersede`) the target rule vanished between lookup and the transactional update | `src/services/pricingRule.service.js`, `src/repositories/pricingRule.repository.js` | Verify the id and tenant |
| `PRICING_RULE_OVERLAP` | 409 | The `pricing_rules_no_overlap` exclusion constraint fires — another rule for the same (tenant, rule type, vehicle type) already covers part of the requested date range | `src/repositories/pricingRule.repository.js` | Supersede the existing rule instead of creating a new, overlapping one — see `07-debugging-playbook.md` for the "first-time create" variant of this error |
| `REFRESH_TOKEN_INVALID` **(shared)** | 401 | The refresh token in the cookie doesn't correspond to any active, non-expired token | `src/services/auth.service.js` | Log in again |
| `REFRESH_TOKEN_MISSING` **(shared)** | 401 | `POST /auth/refresh` called with no refresh cookie present | `src/services/auth.service.js` | Log in |
| `REFRESH_TOKEN_REUSED` **(shared)** | 401 | A refresh token that was already rotated away from is presented again — treated as a possible theft signal; every token for that user is revoked | `src/services/auth.service.js` | Log in again; if this happens unexpectedly, treat it as a signal the refresh token may have leaked |
| `SLUG_UNAVAILABLE` **(shared)** | 409 | Signup couldn't generate a unique tenant slug after several attempts | `src/services/auth.service.js` | Retry, or use a more distinctive business name |
| `TENANT_CONTEXT_MISSING` **(shared)** | 401 | `tenantContext` middleware ran but `req.user.tenantId` was absent | `src/middleware/tenantContext.js` | Should be unreachable if `authenticate` always runs first — see `07-debugging-playbook.md` if you see this |
| `TENANT_NOT_FOUND` **(shared)** | 404 | `GET/PATCH /settings/business` for a tenant id that no longer exists | `src/services/settings.service.js` | Should be unreachable in practice (a valid JWT implies an existing tenant); investigate if seen |
| `USER_NOT_FOUND` | 404 | A user-management operation (`PATCH /users/:id/role`, `PATCH /users/:id/status`) targets a `userId` that doesn't exist in the tenant | `src/services/user.service.js` | Verify the id |
| `VALIDATION_ERROR` **(shared)** | 400 | Any Joi schema validation failure — the single most common error code in the system, since every route runs `validate(schema)` before its handler | `src/middleware/validate.js` (and one direct throw in `src/api/v1/pings.routes.js`) | `error.details.fields` is an array of `{ field, message }` — fix each named field |
| `VEHICLE_ALREADY_EXISTS` | 409 | Creating a vehicle with a `vehicle_number` (canonical, post-normalization) already used by another *active* vehicle in the tenant | `src/repositories/vehicle.repository.js`, `src/services/vehicle.service.js` | Use the existing vehicle, or correct the number |
| `VEHICLE_ARCHIVED_EXISTS` | 409 | Creating a vehicle whose canonical number matches an existing, archived vehicle | `src/services/vehicle.service.js` | Call `POST /vehicles/:id/unarchive` on the returned `vehicleId` |
| `VEHICLE_NOT_FOUND` | 404 | `vehicleId` doesn't exist, or belongs to a different tenant | `src/services/vehicle.service.js` | Verify the id and tenant |

## Domain-error translation (Task 2.6)

`POST /pricing/preview` used to raise a generic `500 INTERNAL_ERROR` when `usage` was missing a field the resolved rule's calculator genuinely required, because the calculators in `src/domain/pricing/` threw a plain `TypeError` in that case, which isn't an `apiError` and so wasn't caught and mapped to a specific `400`. This is fixed: the domain now throws `DomainInputError` (`src/domain/pricing/errors.js`, zero framework dependencies, per the domain's purity rule), and `previewCalculation` (`src/services/pricingRule.service.js`) wraps the `calculate()` call in a `try/catch` that translates any `DomainInputError` into `apiError(400, 'INVALID_CALCULATION_INPUT', ...)`, re-throwing anything else untouched so a genuinely unexpected error still surfaces as a `500`. See ADR-006 and `docs/modules/module-2-master-data/known-issues.md` for the fix record.

## Module 3 error codes

Trip-sheet-specific error codes (`TRIP_NOT_FOUND`, `TRIP_NUMBER_COLLISION`, `INVALID_KM_RANGE`, `INVALID_DATETIME_RANGE`, `NO_APPLICABLE_PRICING_RULE`, `NOT_YET_IMPLEMENTED`, and `INVALID_CALCULATION_INPUT` as raised from `src/services/tripSheet.service.js`) are documented in `docs/modules/module-3-trip-sheets/` once that module's own API/error-reference docs ship — not repeated here, to keep each module's error table the single source of truth for the codes its own routes raise. This table stays scoped to Module 2 (`/vehicles`, `/drivers`, `/customers`, `/pricing`) plus the handful of tenant/auth-wide `**(shared)**` codes every module can hit.
