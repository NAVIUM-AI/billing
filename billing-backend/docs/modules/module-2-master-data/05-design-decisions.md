# Design decisions

_Last updated: 2026-07-18. Reviewers: TBD._

This document explains the *why* behind choices that aren't self-evident from reading the code. Several of these are significant enough to also have a standalone ADR (`docs/adr/`); where that's the case, this section is the short version and the ADR is the long version with alternatives spelled out.

## Why raw SQL, no ORM

Every repository (`src/repositories/*.repository.js`) writes parameterized SQL directly against `pg`, with no query builder or ORM layer in between. The alternatives — an ORM like Sequelize/TypeORM/Prisma, or a lighter query builder like Knex — buy convenience for simple CRUD at the cost of making the genuinely hard parts of this schema harder to express: the pricing-rules exclusion constraint, the JSONB `address` column, the partial unique indexes that make optional fields dedupe correctly, and the constraint-name-to-error-code mapping that gives callers a specific `409`/`400` instead of a generic ORM validation failure. None of these map cleanly onto typical ORM abstractions, and fighting an ORM to express Postgres-specific features tends to cost more than writing the SQL directly. The trade-off accepted is more boilerplate per repository function and no automatic protection against SQL injection beyond discipline — every repository function in this codebase uses parameterized queries (`$1`, `$2`, ...) and never string-concatenates a value into SQL text, but that's a convention enforced by review, not by a library.

## Why paise (integers) for money

See ADR-002 for the full record. In short: JavaScript's `Number` is IEEE-754 double-precision float, and float arithmetic on decimal currency values produces real errors (`0.1 + 0.2 !== 0.3`) that would show up as invoice discrepancies. Storing and computing every monetary value as an integer count of paise (1 rupee = 100 paise) makes every calculation in `src/domain/pricing/` exact addition/multiplication of integers, with zero floating-point risk. The cost is a naming-convention discipline at every boundary — wire input uses `*_rupees` (decimal, user-friendly), storage and internal computation use `*_paise` (integer) — and `src/utils/money.js` is the only place either conversion happens.

## Why versioned pricing rules

See ADR-005. A rate hike can't retroactively change what a trip from before the hike would have cost, which means the pricing_rules table needs to answer "what rate was in effect on date X" for a past `X`, not just "what's the current rate." The `effective_from`/`effective_to` half-open range plus the `pricing_rules_no_overlap` exclusion constraint gives an unambiguous answer to that question at the database level — for a fixed (tenant, rule type, vehicle type), at most one row's range can ever contain a given date, so the lookup (`pricingRule.repository.js#findApplicable`) is a `LIMIT 1` with no tie-breaking logic needed. The alternative considered was snapshotting rates only onto each trip and never versioning the master at all; that alone doesn't solve the "what's the current rate for a new booking" problem, so the master still needs a real history, and Module 3's trip sheets are expected to *additionally* snapshot the resolved rate at trip-creation time as a second safeguard (see ADR-005's Consequences).

## Why B2C and B2B share one table

A single `customers` table holds both individual (B2C) and business (B2B) customers, discriminated by `customer_type`, rather than two separate tables. The two customer types share the overwhelming majority of their columns (`phone`, `email`, `address`, `notes`, `credit_days`, archive state) and every downstream consumer — a trip sheet, an invoice — needs to reference "the customer" without caring which subtype it is; splitting into two tables would mean either a polymorphic foreign key (customer_type + customer_id, no single FK constraint possible) or a shared `customers` supertype table anyway with `b2c_customers`/`b2b_customers` detail tables joined onto it. Given the actual divergence is only a handful of fields (`company_name`, `gstin`, `state_code`, `credit_days`'s practical relevance, and the contacts sub-resource), a single table with conditional-required-field CHECK constraints was judged simpler than either alternative, at the cost of the table having several always-nullable columns that are meaningless for one of the two types (`company_name` for B2C, nothing meaningful for B2B beyond `name` optionally holding a billing-contact name).

## Why GSTIN state cross-check

A GSTIN's first two digits are a fixed numeric code for the state it was issued in (`src/utils/gstin.js`'s `GST_STATE_MAP`), and `state_code` on a customer record drives IGST vs. CGST+SGST tax-split calculation at invoice time (Module 4). If a B2B customer's declared `state_code` disagreed with what their own GSTIN encodes, every invoice raised against that customer would silently compute the wrong tax split — a compliance problem, not just a data-quality one. Cross-checking the two at write time (`customer.service.js`, both on create and on any update that touches either field) catches the mistake immediately with a `400 GSTIN_STATE_MISMATCH` naming both the GSTIN-derived state and what was submitted, rather than letting it surface much later as an incorrect invoice.

## Why canonical + display columns for vehicle_number and phone

Users type the same real-world value — a vehicle's plate, a phone number — in inconsistent formats: with or without spaces, with or without a leading country code, with different separator characters. Storing only the raw input would let formatting differences create duplicate records for the same physical vehicle or the same phone line; storing only a normalized form would lose the human-readable version a staff member actually typed, which reads better on an invoice or in the UI than the compressed canonical form. Splitting into two columns (`vehicle_number`/`vehicle_number_display`, `phone`/`phone_display`) keeps both: the canonical column is the only one ever used for lookups, uniqueness constraints, and duplicate detection, so "KA 51 AK 1031" and "ka51ak1031" are recognized as the same vehicle; the display column is purely for rendering back to a human. `emergency_contact` on `drivers` is the one exception — it's canonical-only, with no display twin, since it's a secondary field that isn't shown as prominently and wasn't judged worth the extra column for this iteration.

## Why soft delete (archive) instead of hard delete

None of the four Module 2 masters expose a `DELETE` endpoint; every one instead has `POST .../archive` and `POST .../unarchive`, toggling an `is_active` boolean. A hard delete of a vehicle, driver, or customer that's already been referenced by a trip sheet or invoice (Module 3/4) would either cascade-delete real transactional history or leave a dangling foreign key; soft delete avoids that entirely; a "deleted" record still exists for any historical record that points to it, it's just excluded from default list views (`includeArchived=false` is the default on every list endpoint) and, for pricing rules specifically, from applicable-rule lookups going forward. Archive/unarchive are both idempotent — archiving an already-archived record returns its current state rather than an error — which keeps the operation safe to retry from a client without needing to track prior state.

## Why customer_type is immutable after create

Switching a customer between B2C and B2B after creation would retroactively invalidate every required-fields assumption already satisfied by the existing row (a B2C row has no `company_name`/`gstin`/`state_code`; flipping it to B2B would leave those still null against a constraint that now requires them) and would change what every past invoice's tax treatment *should* have been, without those invoices actually being recalculated. `updateCustomerSchema` marks `customer_type` `.forbidden()` rather than simply omitting it from the schema, specifically so an attempt to change it gets a direct `400 VALIDATION_ERROR` naming the field, instead of being silently stripped by Joi's `stripUnknown` and producing a confusing "empty patch" error or, worse, a silently ignored no-op. If a customer's type was genuinely entered wrong, the correct fix is to archive the mistaken record and create a new one with the right type — not to convert in place.

## Why pricing rate values are immutable (supersede only)

`updateRuleSchema` allows only `label`, `notes`, and `effective_to` — every rate field, plus `rule_type`, `vehicle_type`, and `effective_from`, is `forbidden()`. This is the audit guarantee versioned pricing exists to provide (see "Why versioned pricing rules" above and ADR-005): if a rate could be edited in place, a past invoice recalculated after the edit would silently use today's rate instead of the rate that was actually in effect when the invoice was issued, and there would be no record that a change ever happened. `POST /pricing/rules/:id/supersede` is the only sanctioned way to change a rate, and it does so by closing the old version's range and opening a new one — the full history of what changed, and when, stays queryable in the table itself rather than requiring a separate audit log.

## Why pure domain module for pricing calculators

`src/domain/pricing/` — `local.js`, `outstation.js`, `performance.js`, `dispatch.js` — has no `require()` of `express`, `pg`, or anything from `src/api`, `src/services`, or `src/repositories`. Every function takes plain objects in and returns plain objects out. This makes the three billing formulas independently testable with `node scripts/test-pricing-calc.js` against known real-invoice numbers, with no database or running server needed, which matters because these are the functions most likely to need a careful audit if a customer disputes an invoice total — being able to point at ~250 lines of pure arithmetic, with no framework code to trace through, and reproduce a number with a one-line `node` invocation, is worth the small extra indirection of `pricingRule.service.js#previewCalculation` doing the unit conversion and DB lookup around the calculator call rather than the calculator doing it itself.

## Why partial unique indexes for optional fields (phone, license, gstin)

`drivers.phone`, `drivers.license_number` (via a table `UNIQUE` constraint rather than a partial index, but with the same NULL-tolerance goal), `customers.gstin`, and `customers.phone` are all optional — a driver or customer record can legitimately have no phone on file — but must be unique *when present*. A plain `UNIQUE` constraint already tolerates multiple `NULL`s under standard SQL NULL semantics (Postgres treats each `NULL` as distinct from every other `NULL`), which is why `drivers_license_per_tenant_unique` is a table constraint; the three phone/GSTIN cases use `CREATE UNIQUE INDEX ... WHERE column IS NOT NULL` (a partial index) for the same effect, made explicit rather than relying on implicit NULL-distinctness, and — for `phone` specifically — because the column also needs an ordinary (non-unique) lookup path in some contexts where a table constraint's implicit index wouldn't be the deciding factor either way; the partial-index form is simply the more common, more explicit Postgres idiom for "unique among non-null values" and was used consistently once chosen for the first case.

## Why FORCE ROW LEVEL SECURITY

See ADR-003. Postgres exempts a table's owning role from that table's own RLS policies by default; this application connects to Postgres as the role that owns every table it created (`billing_app`), so `ENABLE ROW LEVEL SECURITY` alone would provide **zero** actual protection — every query the application ever runs would silently bypass every policy. `FORCE ROW LEVEL SECURITY` closes that gap by applying the policy to the owning role too, which is what makes the two-layer isolation model (`02-architecture.md`) actually a second, independent layer rather than a policy that looks correct in `\d` but never fires in practice. Every business table Module 2 adds runs both statements as a pair; there is no case in this codebase where one is set without the other.
