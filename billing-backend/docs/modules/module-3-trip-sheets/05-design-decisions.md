# Design decisions

_Last updated: 2026-07-19. Reviewers: TBD._

This document explains the *why* behind choices that aren't self-evident from reading the code. Several of these are significant enough to also have a standalone ADR (`docs/adr/`); where that's the case, this section is the short version and the ADR is the long version with alternatives spelled out.

## Why snapshot fields on trip_sheets

Every trip freezes the vehicle number/type, the customer's display name and GSTIN, and the full set of rate columns from whichever pricing rule applied, directly onto the `trip_sheets` row at creation time, rather than joining out to `vehicles`/`customers`/`pricing_rules` on every read. See ADR-005 for the full record: `pricing_rules` is itself versioned, which answers "what rate was in effect on date X" correctly, but a trip's own recorded cost needs to survive even a hypothetical future edit or hard-delete of the rule/vehicle/customer row it was based on — the master answers "what would this cost today, using history," the snapshot answers "what did this specific trip actually cost." The two are expected to agree in the overwhelming majority of cases (a rule's rate columns are themselves immutable after creation; only `supersede` can change them, and that only ever closes the old row rather than mutating it), but the snapshot is what a dispute or audit should trust if they ever disagree. `verify-trip-sheet-outstation.sh` proves this directly by superseding a rule mid-script and re-fetching an already-created trip, asserting every snapshot field and derived total is unchanged.

## Why paise-integer money in trip totals

See ADR-002. Every monetary column on `trip_sheets` (`toll_paise`, `base_amount_paise`, `subtotal_paise`, `net_payable_paise`, and so on) is an integer count of paise, continuing Module 2's convention rather than introducing a different one for transactional data. The alternative — storing decimal rupees, or worse, floating-point rupees — reintroduces exactly the class of rounding error (`0.1 + 0.2 !== 0.3`) that would show up as a real discrepancy between what a trip's stored total says and what its own `breakdown` array, computed independently by the same pure calculator, would recompute. `rupeesToPaise`/`paiseToRupees` (`src/utils/money.js`) remain the only conversion points, applied once at the service boundary on the way in (Joi validates `*_rupees` fields, the service converts before calling the domain layer) and once on the way out for display-formatted fields (`formatINR`, used by the list endpoint's `aggregates.sum_net_payable_rupees`).

## Why one trip_sheets table for all four service_type × billing_mode combinations

`service_type` (`LOCAL`/`OUTSTATION`) and `billing_mode` (`GST`/`PERFORMANCE`) are independent axes on the same table rather than four separate tables or a class-per-combination polymorphic design. The columns that differ across combinations (`base_amount_paise` means base-package price for `LOCAL_PACKAGE`, slab amount for `OUTSTATION_SLAB`, running-km cost for `PERFORMANCE`; `driver_batta_paise` is always `0` for `LOCAL_PACKAGE`) are few enough, and every downstream consumer — the list endpoint, the performance sheet, a future invoice line — needs to reference "a trip" without caring which of the four combinations produced it, the same reasoning Module 2 used for keeping B2C and B2B customers in one table (`docs/modules/module-2-master-data/05-design-decisions.md`). `deriveRuleType(serviceType, billingMode)` (`tripSheet.service.js`) is the single, exhaustively-written mapping from the two stored axes to the `pricing_rule_type_enum` value that actually drives the calculation — reachable but not literally exercised for all four branches by any one task's tests until Task 3.2 completed the outstation half, at which point `verify-trip-sheet-outstation.sh`'s step 6 explicitly confirms all four combinations now work.

## Why trip_tolls is a child table, not JSONB on trip_sheets

An itemized toll list could have been stored as a JSONB array column on `trip_sheets` itself, avoiding a join for the common case of reading a trip with its tolls. It's a separate table instead because tolls have their own identity worth indexing on independently of the parent trip — `idx_trip_tolls_tenant_date` supports a tenant-wide, cross-trip query by `crossed_at` that a JSONB column would require either a GIN index with awkward query syntax or a full table scan to answer — and because a JSONB array offers no way to enforce `trip_tolls_line_per_trip_unique` or `amount_paise >= 0` at the database layer without application-level revalidation on every write. The trade-off is exactly what any child-table design costs: the itemized-tolls path (`insertBatch`, `deleteByTrip`, `listByTrip`) is a second repository file and a second round trip on every trip create/PATCH/read that has tolls, versus zero extra round trips for a JSONB column. This was judged worth it because tolls are the one part of a trip likely to need independent querying or reporting later (a "top toll plazas by spend" report, hypothetically) that a same-row JSONB array actively works against.

## Why lifecycle transitions use SELECT FOR UPDATE

Every mutation to an existing trip (`updateTripSheet`, `finalizeTripSheet`, `cancelTripSheet`, `markTripInvoiced`) opens by calling `tripRepo.findByIdForUpdate`, which issues `SELECT ... FOR UPDATE` inside the caller's transaction. The alternative — reading the trip with a plain `SELECT`, deciding whether the transition is valid in application code, then issuing the `UPDATE` — has a race window between the read and the write: two concurrent requests can both read the same "current" status, both independently conclude their own transition is valid, and one of them silently clobbers the other's work (or, worse, both apply and the row ends up in a status neither request actually intended, depending on statement ordering). `FOR UPDATE` closes that window by making a second concurrent transaction's own `findByIdForUpdate` call on the same row block until the first transaction commits or rolls back, so by the time the second transaction's read completes, it's reading post-commit state and will correctly see the first transaction's transition already applied.

## Why finalize/cancel use guarded UPDATE (WHERE status = $from)

Every transition-applying `UPDATE` (`tripRepo.transitionStatus`, `tripRepo.updateDraft`) includes `AND status = $fromStatus` in its `WHERE` clause, on top of the row lock described above. This is deliberate belt-and-suspenders, not redundant defensiveness for its own sake: the guarded `WHERE` clause means that even in a hypothetical scenario where the row lock's protection were somehow bypassed or misapplied, the `UPDATE` itself cannot silently apply against a status it didn't expect — it simply matches zero rows, and the service layer treats a zero-row result as a `409` (`TRIP_STATUS_CHANGED`, `TRIP_STATUS_CHANGED_DURING_UPDATE`) rather than assuming success. The cost is a small amount of extra specificity in every transition query and an extra "did this actually update a row" check in the service after every write; the benefit is that the concurrency-safety property of this module doesn't rest entirely on one mechanism (the lock) being perfectly correct in every future edit to this code.

## Why PATCH only works on DRAFT trips

`updateTripSheet` guards on `trip.status !== 'DRAFT'` and rejects with `409 TRIP_NOT_EDITABLE` otherwise; `tripRepo.updateDraft`'s own `UPDATE` additionally guards `WHERE status = 'DRAFT'` as the same belt-and-suspenders pattern described above. This reflects the planning-context requirement that ops staff need to fix mistakes freely before a trip is acted on, but that `FINALIZED` is meant to be the point after which a number is stable enough to build a billing or reporting decision on (`01-planning-context.md`). Allowing edits past `FINALIZED` would mean any report or invoice draft built from a finalized trip could silently go stale the moment someone edits it — the alternative this module chose instead is that a `FINALIZED` trip with a genuine error has to be `CANCELLED` (with a reason, forming an audit trail) and re-entered, rather than quietly amended in place.

## Why list aggregates for the FILTERED set, not the page

`GET /trips`'s `aggregates` object reflects every trip matching the request's filters, not just the `limit` rows actually returned on that page. The alternative — aggregating only the current page — would answer a question nobody asks ("what's the sum of these 25 rows specifically") instead of the one ops actually wants ("what does this filtered view add up to in total"), and would change value every time the caller changed `limit`/`offset` with no filter change, which is confusing UI behavior. The repository achieves this without a second hand-maintained `WHERE` clause by building one `wheres`/`params` array and reusing it verbatim for both the paginated data query and a second, unpaginated aggregates query (`tripSheet.repository.js#list`) — a design specifically chosen to prevent the two queries' filter logic from drifting apart as new filters are added in the future, which copy-pasting the clause into two separate SQL strings would risk.

## Why sort_by has a hardcoded whitelist

`sort_by` on both `GET /trips` and the performance-sheet endpoints is validated against a fixed `.valid(...)` list in Joi and *again* against a hardcoded `SORT_WHITELIST`/`PERF_SORT_WHITELIST` object in the repository layer, rather than accepting any column name the caller supplies. Postgres has no way to parameterize a column or identifier name the way it parameterizes a value (`$1`, `$2`, ...), so an `ORDER BY` clause built from a caller-supplied string is a SQL-injection surface if that string isn't constrained to a known-safe set before it's ever interpolated. The two-layer whitelist is deliberate defense in depth: the Joi-level check is the fail-early UX (a bad `sort_by` gets a clean `400 VALIDATION_ERROR`), and the repository-level check is a hard backstop that treats an unrecognized value as a bug rather than user input — reaching that branch means the validator's own whitelist was somehow bypassed, so it throws a plain `Error` (an unhandled 500) instead of trying to degrade gracefully, on the theory that a security boundary failing loudly is safer than one failing quietly.

## Why performance sheet is a projection, not a table

`billing_mode = 'PERFORMANCE'` is a value on the same `trip_sheets.billing_mode` column every other trip uses, not a separate entity or a separate table populated by some sync process. The performance-sheet endpoints (`GET /trips/performance-sheet`, its CSV counterpart) are pure reads: `listPerformanceRows` runs the identical WHERE-composition pattern the general list endpoint uses, with one additional fixed filter, and the service groups/formats the result — no write path exists that's specific to "performance sheet" as a concept. This was chosen over a materialized or separately-maintained performance-tracking table because a `PERFORMANCE` trip is, in every structural sense, exactly the same kind of row as a `GST` trip (same lifecycle, same PATCH/finalize/cancel rules, same tenant isolation) — the only thing that differs is which pricing calculator ran and how ops chooses to *view* the results afterward. Keeping it a projection means every guarantee the general trip machinery already provides (snapshot immutability, row-locked lifecycle transitions, RLS) applies to performance trips automatically, with nothing separate to keep in sync.

## Why CSV export has a hard row cap

`getPerformanceSheetCsv` (via `getPerformanceSheet`) rejects with `400 EXPORT_TOO_LARGE` if the filtered row count would exceed `MAX_ROWS` (10,000), rather than silently truncating the export or streaming an unbounded response. A CSV export that silently drops rows past some limit is a worse failure mode than an explicit error — a user who didn't notice the truncation could make a real decision off an incomplete cost sheet. Rejecting outright with a clear code, alongside `error.details.max_rows`, tells the caller exactly what happened and points at the fix (narrow the filter with a date range or customer). The 10,000 figure itself is a practical ceiling chosen for "large enough that no real tenant's realistic date-range query should ever hit it, small enough that the in-memory row set and string-building the CSV renderer does stays cheap" — not derived from a specific measured limit.

## Why lifecycle domain module is pure (no framework imports)

`src/domain/tripLifecycle/` has zero imports from `express`, `pg`, or anything under `src/api`/`src/services`/`src/repositories`, mirroring `src/domain/pricing/`'s existing design (ADR-006) and applying the same "domain modules throw a dependency-free error class; services translate at the boundary" pattern (the module defines `LifecycleError`, following `DomainInputError`'s shape). This keeps the entire legal-transition table — what can move to what — expressible and testable as a handful of `Set`s with no framework code to trace through, and makes it directly reusable by Module 4's invoice-issue flow, which needs the exact same `DRAFT`/`FINALIZED`/`INVOICED`/`CANCELLED` transition rules to validate its own `FINALIZED → INVOICED` call rather than re-encoding them. One deliberate deviation from the pattern as literally specified: the service's `assertTransition` helper (`tripSheet.service.js`) calls `isValidTransition`/`allowedTransitions` directly and throws `apiError` itself on failure, rather than having the domain module throw `LifecycleError` and the service catch-and-translate it the way `pricingRule.service.js#previewCalculation` does for `DomainInputError`. `LifecycleError` exists in the domain module (mirroring the pattern's shape for future use) but nothing in this module currently throws or catches one — `isValidTransition` is a boolean-returning function, not a throwing one, so there's no domain-level exception for the service to translate in this particular case. This is a smaller, boolean-check-shaped variant of the same underlying principle (a pure domain function decides the rule; the service owns the HTTP-shaped response), not a full instance of the catch-and-translate flow ADR-006 documents.
