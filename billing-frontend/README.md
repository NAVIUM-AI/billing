# Navium Billing — Frontend

Vite + React + TypeScript + Tailwind + a narrow, hand-maintained set of
shadcn/ui-style components. Talks to `billing-backend` (Express/Postgres)
at `VITE_API_URL`.

## Running

```bash
npm install
npm run dev       # http://localhost:5173
```

The backend must be running separately on `:8000` (`npm run dev` inside
`billing-backend/`), with `FRONTEND_URL=http://localhost:5173` in its
`.env` so CORS reflects this origin with `credentials: true` — without
that, the HttpOnly refresh cookie won't flow and login will silently
not survive a page reload.

`npm run build` runs `tsc -b && vite build` — a TypeScript error fails
the build, not just a lint warning.

## Env vars

| Var | Purpose |
| --- | --- |
| `VITE_API_URL` | Base URL of the backend API, e.g. `http://localhost:8000/api/v1` |

Copy `.env.example` to `.env.local` (gitignored) to set it locally.


### Conventions for adding a new feature

- One feature = one folder under `features/<name>/`.
- A feature owns its own `<name>.api.ts` (typed functions wrapping
  `apiClient` calls + Zod parsing), its screens/components, and any
  feature-local hooks. Don't reach into another feature's internals —
  share through `lib/` or `types/` instead.
- Shared, dumb UI primitives → `components/ui/`. Shared page chrome →
  `components/layout/`. Cross-feature logic that isn't UI → `lib/`.
- State discipline: **server state = TanStack Query, client/UI state =
  Zustand, form state = React Hook Form.** Don't reach for `useState`
  + a `useEffect` fetch when TanStack Query already solves that
  problem, and don't put server data into a Zustand store.
- No prop drilling past 2-3 levels — reach for context or a store
  instead of threading props through components that don't use them.

## Auth architecture (locked in by this task — read before touching)

- The access token lives **only** in memory (`stores/auth.store.ts`,
  no `persist` middleware). It is gone the instant the page reloads,
  by design.
- The refresh token is an HttpOnly cookie the backend sets and reads —
  no frontend code ever sees its value (confirmed: `document.cookie`
  does not expose it, and it is never written to `localStorage`).
- On every app mount (`App.tsx`), a bootstrap effect calls
  `POST /auth/refresh` to silently re-derive a session from that
  cookie, then `GET /auth/me` to hydrate the user (the refresh
  response itself does not include a user object — see
  `lib/schemas/auth.ts`'s comment). This is what makes "hard-refresh
  the browser, stay logged in" work.
- **Both** the bootstrap effect and the axios response interceptor's
  silent-retry-on-401 path call the exact same exported
  `refreshAccessToken()` in `lib/api.ts`, never `POST /auth/refresh`
  directly. This single-flight guard exists because the backend has
  refresh-token **reuse detection**: if the same (already-rotated)
  refresh token is presented twice, the backend revokes every refresh
  token that user has, everywhere. Two concurrent, uncoordinated calls
  to refresh — which really happens, e.g. React StrictMode's dev-mode
  double-effect-invocation, or two browser tabs racing an expiry at
  the same moment — will trip this and kill the whole session. This
  was an actual bug caught by browser-testing this task, not a
  hypothetical; see the git history on `lib/api.ts` and `App.tsx`.
- The interceptor never auto-redirects on a failure of the refresh
  call itself — only the two callers above (bootstrap, and the
  retry-catch block) decide what a failed refresh means in their own
  context. A bootstrap failure (no cookie yet, e.g. a first-time
  visitor) is not an error; a mid-session retry failure is a dead
  session and does redirect.

## A note on shadcn/ui components

`components/ui/*` are **hand-written**, not generated by `npx shadcn
add`. As of this task, the latest `shadcn` CLI (v4.x) ships a
fundamentally different setup (its own packaged CSS import, an
oklch-based preset system, no more `tailwind.config.js`-driven
theming) than the classic New York/Slate/CSS-variables flow this
project uses with Tailwind v3. Running the new CLI against this
project does not work cleanly. `components.json` is kept as a
reference/documentation artifact in the classic schema shape; when
adding a new primitive (F2+), the reliable path is to hand-copy the
component source from the shadcn docs (or an existing New-York-style
project) rather than running `npx shadcn@latest add <x>` and hoping
it reconciles with this setup. If the CLI's architecture converges
back with a Tailwind-v3-compatible flow later, this note can go.
